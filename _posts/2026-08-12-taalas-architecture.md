# Introduction

Taalas (https://taalas.com/) launched their HC1 chip on February 19th, 2026. Their goal: create an accelerator designed to produce the highest amount of tokens per second by targeting specific LLM transformers (in the case of the HC1, Llama 3.1 8B). Built on TSMC's 6nm process node, its die size was about 815mm^2 (near reticle limit), with about 53 billion transistors.

The really interesting thing about this chip that excites me is the fact that Taalas claims to be able to serve about 16,960 tok/sec to a given user (https://taalas.com/products/). For context (as shown below), Taalas' own study reports that an NVIDIA H200 delivers only 230 tok/sec, with Cerebras reaching a mere 1981 tok/sec (about 8.6x worse than Taalas).

![Taalas's claimed baseline](../assets/images/taalas_baseline_claim.png)

The obvious downside of this is that they achieve this remarkable throughput by hardcoding the model into the silicon, meaning that they can only run Llama 3.1 8B on their HC1 (there is some nuance to this, but for now that is the high level claim)

Now I am extremely interested in how they achieved this, and whether there is any takeaway from their methodology. I tried out their chatbot (https://chatjimmy.ai/), and the response time is basically instant (sometimes I couldn't even tell it responded because it came back so fast it didn't clock to me).

My first instinct to understand their architecture was to look at Taalas' patents and some of the patents from their founders. A list of the patents I looked at is as follows:

There are MANY more patents filed under Ljubisa Bajic, Lejla Bajic, and Drago Ignjatovic (CEO, COO, and CTO respectively), but these are the ones I found to be the most related to Taalas and filed during the time Taalas was actively developing their HC1. We can break these patents up into four sections: Core computation/multiplication, ROM cell design, LLM fine-tuning circuit support, and dense memory. I will do my best to give my thoughts and takeaways from these patents, but I also highly recommend reading them yourself (and talking to me about them)!


## Core Computation/Multiplication

The patents I explored for the core computation and multiplication were Patents 1 through 3.

Patent 1's goal is to discuss "computational architectures for accelerating vector multiplications", specifically matrix multiplication. The key insight that underlies this patent is that as LLM parameters scale to the billions and trillions, the number of available values for a given parameter is limited. For example, a 4-bit quantized data type can only have 16 possible values, and an 8-bit quantized value can only have 256 different values. With more and more models utilizing aggressive quantization strategies like these, Taalas aims to exploit this pattern by basically having dedicated multipliers for each potential type of multiplication (i.e. mult x, 0; mult x, 1; mult x, 2; ...; mult x, 15), multiplying a given quantized value by every single potential value it could be multiplied by, and using a "set of readable cells" (i.e. ROM) to choose which multiplication value to use.

This is a lot of information, but a more digestible way of thinking about it is like this: each parameter of a transformer (ignoring fine-tuning for now) is a fixed value (let's call this value x). If x is a quantized value of 4 bits, there are only 16 possible values it can hold. More importantly, there are only 16 possible multiplication values that can come out of multiplying x by another 4-bit value. If we do all 16 multiplications in parallel while pulling a selector value for the parameter out of ROM, we can speed up the time it takes to do a multiply.

This is one of the big points established by this patent, but it's not completely clear why this is important. With a traditional multiplication, you need to pull your two values in from memory (either SRAM or HBM), send them through a general-purpose multiplier (which, to be performant across multiple values, must be larger and typically takes multiple cycles), and then store the value back into memory. With this setup, Taalas can pull a value in from SRAM, compute all possible values it can produce in parallel with dedicated multipliers (one for 0, one for 1, ..., one for 15), and then, in parallel with this computation, have ROM select which multiplier output it wants to store in memory once done. This means the path an operation must travel is from SRAM to a highly optimized multiplier and then finally back into memory, which is extremely efficient.

This sequence of operations dictates one multiplication, and so Taalas achieves matrix/vector multiplication by accumulating these individual multiplication values over the course of multiple cycles and multiple weight-multiplier selections. One weight matrix can be represented as multiple rows of ROM (again, what the patent refers to as readable cells). For each multiplication, the mesh that connects the cluster of ROM for a given matrix can configure, through the value in the ROM, which multiplier it wants to accumulate. This exact mechanism is what Taalas refers to as their "configurable connectivity mesh", which can be formed in various different ways, but the one I think is the most interesting is through a single transistor. The weight-selection ROM, when read out, gets decoded and selects the specific multiplier line it wants to accumulate by driving the gate of a single transistor (per multiplier output bitline), which allows the value of the multiplier to flow into the mesh and to the accumulator.

Now this is where Patent 2 comes in, because that single transistor per output bitline is the simplest way to picture the selection, but it isn't free. If you think about it, using the selection as physical switch through the transistors in the mesh means you need a dedicated transistor and its routing for every possible connection you might want to make, and once you scale that out across every parameter in a matrix the wiring to route all of those possible connections becomes a massive amount of interconnect. Patent 2 is basically the exact same core idea (precompute all 16 products, store the choice in ROM), but it swaps out how the selection happens with a denser solution. Instead of the ROM driving a transistor that gates one multiplier line into the mesh, the ROM now stores an address (the patent calls it "a set of addresses that is associated with the set of values of the set of parameters"), and that address is what drives a selector/multiplexer to pick which multiplier output gets passed through.

With the one-transistor-per-line mesh, the cost of selecting scales with the number of possible connections you're physically routing, which is what blows up the interconnect area. With the address-into-a-mux approach, you only need enough ROM bits to encode the address (one of 16 outputs is just a 4-bit address per parameter), and the selector hardware stays basically the same size no matter how big the block of ROM gets. So you're taking what was a big spread-out switch fabric and compressing it down to a compact address decode, and since the patent points out each of those readable cells can be a single access transistor plus a storage element, you can make the number of stored parameters really large at minimal cost. It's the same multiplication trick from Patent 1, just with way less silicon spent on the act of actually choosing the answer.

The benefit of both of these patent implementations is that they allow Taalas to reconfigure their chip to serve other models at tape-out time. Instead of hardcoding the weights into ROM, Taalas hardcodes the selection of the multiplier values in ROM. This translates a multiply of a non-weight value with a weight value into a multiply of a non-weight value with all 16 multipliers, and lets the ROM select which one we want. If we have the ability to change which multiplier value we want, we then effectively change the weights that we multiply by without ever changing the underlying SRAM/multiplier hardware, only the ROM with the selection. So to run another model on Taalas' HC1 chip, they would just need to replace their mask ROM with the new selector values.

This obviously has some bottlenecks, as we can only store as many weight selectors as there is ROM to hold them (Llama 3.1 8B is tiny compared to the gigantic models we have nowadays). Additionally, this requires 16 multipliers to perform one operation, which is still a high area overhead for a single operation. Let's say you want to do more than one multiplication at a time now; you need 16 * [number of concurrent multiplication operations] to actually do all of this. Granted, these multipliers are all highly optimized for area, power, and performance and are small in comparison to the size of a traditional multiplier, so one could argue this is inconsequential. A larger issue someone might think to ask is how Taalas is able to perform such a high number of operations per second, and this is really where the whole ROM vs HBM thing becomes the entire point of the architecture.

The thing to realize is that on a traditional GPU, token generation (the decode phase) isn't actually compute bound, it's memory bandwidth bound; to spit out a single token the hardware has to stream basically every weight in the model out of HBM, across the bus, and into the compute cores, so your throughput ceiling is really just the memory bandwidth divided by the number of bytes you read per token (https://dev.to/kavs/why-memory-bandwidth-matters-more-than-tflops-for-llm-inference-4e6g, https://turingpi.com/llm-tokens-per-second-memory-bandwidth/). This is exactly why Taalas' own chart pegs an H200 at only ~230 tok/sec for a single user; an H200's HBM3e tops out around 4.8 TB/s (https://turingpi.com/llm-tokens-per-second-memory-bandwidth/), and streaming the ~16 GB of Llama 3.1 8B weights (plus the growing KV cache traffic) once per token lands you right in that few hundred tokens per second range.

Now let's run that same math for Taalas' claimed 16,960 tok/sec. If you had to fetch the weights from any kind of bus attached memory, you'd need roughly (weight bytes) x (tokens/sec) of bandwidth; even at an aggressive 4-bit quantization (~4 GB for 8B params) that's about 68 TB/s, and at 8-bit it's ~135 TB/s, which is something like 14 to 28x what an H200's HBM can actually deliver (https://turingpi.com/llm-tokens-per-second-memory-bandwidth/). No amount of HBM stacking realistically gets you there. The only way to satiate that kind of instruction throughput is to just stop moving the weights at all, and that's precisely what the mask ROM selectors buy you; the weights never leave the die, and every multiply reads its selector out of a ROM cell that physically sits right next to the multiplier it drives (https://www.buysellram.com/blog/17000-tokens-second-is-taalas-hardwired-silicon-the-ultimate-solution-to-the-ai-memory-wall-and-hbm-shortage/, Patent 1).

That proximity isn't just a power argument, it's a timing one too. Interconnect delay is dominated by the RC product of the wire, and the really important part is that this RC delay grows with the *square* of the wire length (https://pages.hmc.edu/harris/class/hal/lect4.pdf); global wires that have to span the whole die can end up costing as much delay as the logic itself, to the point where designers chop them up with repeaters just to keep them sane (https://research.cs.wisc.edu/multifacet/theses/bradford_beckmann_phd.pdf). By keeping the selector ROM right up against the multiply-selectors, the wire between them is tiny, so the RC delay is tiny, and the selector value can be read out and applied every single cycle without the ROM read ever becoming the critical path. Contrast that with an HBM read, where the value has to cross the package, the bus, and the on-chip global interconnect before it ever gets anywhere near a multiplier.

The last piece that ties this all together is that this multiply-select ROM block isn't one big shared structure; it's a motif that just gets replicated all over the die, basically a local cluster of selector ROM plus its own dedicated multipliers for each weight matrix, and by extension for each layer of the transformer. Because every layer's weights are stationary in their own little patch of silicon (a weight-stationary, spatial dataflow where you bring the compute to the data instead of the data to the compute (https://www.buysellram.com/blog/17000-tokens-second-is-taalas-hardwired-silicon-the-ultimate-solution-to-the-ai-memory-wall-and-hbm-shortage/)), you can light up all the layers concurrently and pipeline them instead of time-sharing one memory port. This effectively turns what would've been a single ~TB/s HBM channel into the entire die's worth of ROM being read in parallel, and that's really where the aggregate on-chip "bandwidth" needed to hit tens of thousands of tokens per second comes from. The cost, obviously, is area; you're paying silicon to give every single weight in the model its own permanent home on the chip, which is exactly why this only works for a model small enough (Llama 3.1 8B) to physically fit in the first place.
